# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Fixed

- **A continue that fails after a trim is retried.** Before, when the trim worked but the continue did not go through (every try failed, or the host did not come back), the watcher showed one "resume needed" notification and never tried again: later runs found no session, because a restarted host holds no lock on it until a message loads it, and network and stall resume treat a trim stop as deliberate. The same design left an agent idle for 22 hours on a real machine. The trim run now records the owed continue in `<stateDir>/pending-continue-<instanceName>.json`, and every later run retries it once before looking for the session, with a message that says when the trim happened and asks the agent to check git state and running work first. It is cleared when it goes through or when the log shows the session was resumed by hand; after `watch.pendingContinueMaxTries` (default 6) runs it notifies once. `--dry-run` reports what it would do. The scheduled watcher's time limit now allows for two rounds of continue tries; run `install` again to update an existing schedule.

## [0.2.0] - 2026-11-08

The first version on npm, and the first proven on a real session: the kit trimmed a goal-loop session's log at a safe point (13 MiB to 0.6 MiB) and resumed it, through three batches of a private LoopBoard rehearsal on Windows.

### Added

- **Install from npm** (`npm install -g copilot-forever`), and **`copilot-forever setup`**: the goal-loop bootstrap for the repository in the current folder (`--repo` names another). From an npm install it skips `npm ci` and `npm link`. `npx copilot-forever setup` works too, except for the keep-alive schedule: `install` and `setup --start` refuse to run from the npx cache, which npm can clear, and say to install with `npm install -g`; `install` warns when the kit sits in a project's own `node_modules`, which a clean install or prune removes. The printed next steps use the command that will work: `copilot-forever` for a global install, `npx copilot-forever` under npx, otherwise `node` with the path to the kit.
- **`copilot-forever protect`**: makes GitHub require a pull request for every change to the default branch, admins included, so an agent (which pushes as you) cannot push to it. Existing protection is left as it is. When GitHub refuses, for example a private repository on a free plan, it says why. Setup's next steps now say to push the scaffolding and then run it.
- **Fixes for missing tools**: setup's prerequisite check says how to fix each missing tool (where to install git, gh and Node, `gh auth login`, how to put VS Code's `code` command on PATH on each platform), and `doctor` says what to do for a missing repo folder or agent file, a `code` command that fails, a host that isn't running and a session that isn't open.
- **Effort per role** (`effort` in the goal-loop config): demo and default levels Architect max, Orchestrator high, Builder high, Diff Reviewer max. The bootstrap writes the subagents' levels to Copilot's user settings (`subagents.agents.<name>.effortLevel`, verified to apply on the VS Code agent host); the Orchestrator's level goes in the chat's model picker, and Ralph mode passes it as `--reasoning-effort`. `--no-effort` leaves the settings alone.
- **Timing report** (`copilot-forever report`): reads a session's log, and its trim archives, and shows where the time went. Every minute is in one bucket (subagents, Orchestrator, waiting for a message, waiting on background commands or sleeps, quiet, stopped), then per-role totals and one row per subagent run with effort, model and tool time, tool calls and tokens, plus Copilot's usage figures. Markdown, `--json` or `--out <file>`. Streams the log, so it handles the largest sessions (a 949 MiB log takes a few seconds).
- **Simpler code, own leftovers, written assumptions** (goal-loop agents): the standing orders ask for the simplest code that meets the acceptance criteria (no options, abstractions or error handling the issue does not need), removing what a change made unused while leaving other dead code alone, and writing down the reading taken where an issue is ambiguous instead of guessing silently. The Builder reports its assumptions and the dead code it left; the Diff Reviewer checks size and assumptions (size findings are repaired by deleting code in the round that found them; deleting code the change itself added that nothing references needs no further review round, and anything else gets a delta review, which counts as a round); the Architect's plan lists its assumptions and rejected readings for plan approval. Prompted by the four principles in [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills), adapted for a loop that runs without a person to ask.
- **Change size in the timing report**: a Changes section with the commits made in the session's span, lines changed per commit (median and largest) and Diff Reviewer runs per commit, from `git log` in the repository. Only commits whose committer is the repository's own `user.email` count, so GitHub's squash-merge commits are left out; branches deleted after merging still count through the reflog. Only changes under the configured folder count, so a folder inside a larger repository reports its own. Without a `user.email` every committer counts, and the report says so; when git fails, the section says why.
- **Agent name prefix** (`agents.namePrefix`, default `Goal `): the agents are Goal Orchestrator, Goal Architect, Goal Builder and Goal Diff Reviewer, so their user-wide effort settings never collide with other agents named Architect or Builder.

- **Goal loop** (`templates/goal-loop/`): Orchestrator, Architect, Builder and Diff Reviewer custom agents for GitHub Copilot; shared standing orders; a receipted gate script (`gate.mjs`); a handoff template; and a config for models, gate command, caps, merge policy and labels. Safe defaults: one human plan approval (`APPROVE PLAN`), caps, a STOP file, PRs only with no auto-merge, and a reviewer on a different model family (bootstrap refuses the same family).
- `bootstrap.mjs` and `copilot-forever goal-loop`: one-command setup on a new machine. Checks prerequisites, installs the kit, renders the templates into a repository without overwriting its own files, writes its keep-alive config, and prints the manual steps. `--dry-run` writes nothing.
- **Ralph mode** (`copilot-forever loop --mode ralph`): the same agents run as fresh `copilot -p` Orchestrator runs, one step per run (plan, file issues, one batch), with the agent and model pinned on every call. It stops on an empty queue, the STOP file, the caps, or a stall guard. Plan approval is `copilot-forever loop approve-plan`, bound to the plan's hash. Each run is logged to `.goal-loop/ralph/runs.jsonl`. Dry-run mode. Needs no standalone host, trim or AHP client.
- `bootstrap.mjs --start`: also schedules the watcher and starts the standalone host (persistent mode).
- The Orchestrator accepts a goal pasted into the chat and saves it to `.goal-loop/GOAL.md`.
- Demo (`demo/`): the LoopBoard goal, reproduction steps for both modes, a demo config, and the video script.
- README: "Persistent session or Ralph loop?" comparison.
- [Orchestrator map](docs/orchestrator-map.md): the goal loop end to end, with diagrams of the whole loop and of one batch, the roles, every decision point, where state lives, where a person comes in, what code enforces versus what the agents' instructions do, and how the keep-alive kit fits in.
- **Network resume**: when the session's last turn died on a network error (DNS, connection, timeout, 5xx), the watcher sends a continue once the model API answers again. Never after auth, quota, rate-limit, policy, cancel or unrecognised errors; at most `resume.maxTries` continues per error and `resume.maxPerDay` across errors, then one notification. Configured under `resume`.
- **Stall resume**: when the agent's last working turn launched background work (an async shell or a background task) and ended to wait for it, but no completion notification ever woke it, the watcher sends a continue naming that work after `stall.quietMinutes` of quiet (or the longest `Start-Sleep` in that turn plus 5 minutes). Never after `task_complete` or `ask_user`, or when the log ends in an error; at most `stall.maxTries` per stall and `stall.maxPerDay` in all, then one notification. Seen on a real standalone host: after a network error, no completion notification arrived for the rest of the session, and the orchestrator sat idle for 5.5 hours. Configured under `stall`.

- **Stale host status notice** (`watch.staleHostMinutes`, default 30): when the host still lists the session as running although the log's last turn ended that long ago, the watcher notifies once per episode (open the chat; if it shows as running with no question or background work pending, press Stop). A turn that ended on an `ask_user` question is not counted; a question asked in plain text is not detected, so the notice asks you to check. Such a stale listing blocks trims and resumes, and the watcher never overrides the host. Seen on a real host: the agent stopped for a trim, the host listed the finished turn as running for over 2 hours, and the trim waited the whole time with no notice.
- **Session open in two hosts**: the watcher notices a session held by a live runtime under this host and by another runtime at once (two runtimes writing one log), logs it, and notifies once per episode, naming the other host and which copy to close; `doctor` warns, and a trim of such a session is refused with nothing stopped. Stale locks whose PID was reused are ignored (the process must have started before its lock was written); the process table now records start times for this. Seen on a real machine: the Agents window opened another repository's session (run by its own host on localhost:47801) through this kit's host on localhost:47811, and a `/compact` and a trim message meant for the kit's session went to that second copy.

### Changed

- Default models: `claude-sonnet-5.5` for the Orchestrator, Architect and Builder; `gpt-6.1-sol` for the Diff Reviewer.

### Fixed

- The watcher no longer misses the host for a run when `code agent ps` prints its own log lines (such as `[2026-11-06 22:57:42] info …` while the CLI updates itself) ahead of the JSON. Seen on a real Windows host.
- Windows: the scheduled host task no longer deadlocks. With the schedule installed, its own `host start` asked the scheduled task (itself) to start the host and waited out the start timeout for a port nothing would open. So with the schedule installed the host never started at logon, `host start` failed after 3 minutes, and the watcher's restart after a trim left the host down. The task now runs `host start --direct`, which spawns the host itself. **Existing installs keep the old task until you run `install` again**; `doctor` now warns about an install from an older kit. `--direct` is also available by hand.
- Windows: `uninstall --stop-host` now stops the running host. Before, it deleted the scheduled tasks and reported "uninstalled." while the host kept running (seen on a real Windows install: deleting a task did not stop the process it started). It now takes the watcher lock (refusing, with nothing changed, while a watcher run such as a trim is in progress), deletes the watcher task, stops the host and checks that its port has closed, then deletes the host task. If the stop fails, the host task stays installed and the error says what is left and what to do next.
- A trim no longer fails to restart the host when the killed host's listening socket outlives it briefly (seen on Windows): `stopHost` waits up to 30 s for the port to close, so the restart doesn't find the port "already listening" and skip the start.
- Windows: the scheduled tasks no longer flash a console window on every run. They now start through `conhost.exe --headless`; run `install` again to update existing tasks.
- The agent snippet now tells the agent what to do with a network-resume "Continue." message, not only a trim one.
- The watcher lock and the host log are now per instance (`watch-<instanceName>.lock`, `host-<instanceName>.log`), so two instances sharing a state folder no longer block each other.

## [0.1.0] - 2026-11-04

First public version: a generic, cross-platform port of a working Windows setup (PowerShell and Python scripts) that keeps one orchestrator session alive. Reference implementation in validation: a full automatic trim cycle has not yet completed on a real session.

### Added

- `host start|stop|status`: the standalone VS Code agent host on localhost with an owner-only connection token, started from a clean environment, with the token masked in its log. `--foreground` supervises it for systemd and launchd.
- `trim`: cuts `events.jsonl` at the latest compaction whose `session.compaction_complete` has `success: true`. It keeps header events, re-parents orphans, archives the full log first, replaces the log atomically and verifies the result. It refuses while the session is in use. `--copy <new-id>` writes a trimmed copy instead.
- `watch`: a status file for the agent, and a trim on request at an agent-chosen safe point. The session must be idle on two checks. Safety checks run before anything is stopped. Then the host is stopped, the log trimmed, the host restarted, the continue message sent and a notification shown.
- `continue`: sends the continue message over the Agent Host Protocol using Microsoft's `@microsoft/agent-host-protocol` client. It reuses the last user message's model and custom agent, refuses a busy chat, and succeeds only when the agent starts working. `--probe` is read-only.
- `install`/`uninstall`: Windows Task Scheduler, macOS launchd agents, Linux systemd user service and timer.
- `doctor`, `init`, `snippet`; `--dry-run` on every command.
- Safety gates: Copilot CLI and runtime major-version check; a log-schema check that refuses unknown layouts.
- Desktop notifications on Windows (toast), macOS (`osascript`) and Linux (`notify-send`), always logged as well.
- Agent-side snippet for any `.agent.md`: the safe-point rule, handoff addendum, and status and request file formats.
- Tests: synthetic `events.jsonl` fixtures (including failed and in-progress compactions), a fake AHP WebSocket server, and an end-to-end trim cycle against a fake host. CI on Windows, macOS and Ubuntu with Node 22 and 24.
